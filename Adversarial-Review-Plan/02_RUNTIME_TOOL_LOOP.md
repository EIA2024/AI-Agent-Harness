## Runtime / Tool Loop 专项\n\n### A. P0-001 的精确根因\n当前链路：`build_context()` 生成 `_cached_context` → `decide()` 发出 tool call → `tool_request/execute()` → `observe()` 把 assistant tool_call frame + tool result 写入 `messages` → 回到 `decide()`。问题是 `observe()` 没有让 `_cached_context` 失效，因此下一轮 `decide()` 可能继续使用工具调用之前的 context。\n\n### 最小安全补丁\n在所有会影响 prompt 的节点（observe、approval decision、plan changed、memory/context mutation）显式返回 `_cached_context: None`。同时新增 regression test：FakeProvider 不再只按脚本返回，而是检查第二个 `ModelRequest.messages` 中存在 `role=tool` 且 content 含结果。\n\n### 长期正确设计\n不要维护一个无版本 cache：\n```python\nclass ContextSnapshot(TypedDict):\n    revision: int\n    built_from_messages_revision: int\n    messages: list[dict]\n    token_count: int\n\n# 每次 state.messages 改变：\nstate["messages_revision"] += 1\n# decide only reuses when snapshot.built_from_messages_revision == messages_revision\n```\n这样 future 节点不会再次忘记 invalidation。\n\n### B. MAX_TOOL_CALLS 不应承担循环检测\n`MAX_TOOL_CALLS=5` 保留为 hard budget，但新增：\n- `max_total_tool_calls`\n- `max_same_signature_repeats`（推荐 2）\n- `max_tool_failures`\n- `tool_budget_deadline_ms`\n- signature=`tool_name + stable_json(arguments)`\n如果相同 signature 连续出现且上一次 success，第二次调用前把“已得到该结果”反馈给模型；若模型仍重复，则进入 `loop_guard`，而不是再执行副作用工具。\n\n### C. ToolResultEnvelope\n禁止把 connector 任意 data 原样塞进 state。建议：\n```python\n@dataclass\nclass ToolResultEnvelope:\n    success: bool\n    text_preview: str\n    structured_preview: dict | list | None\n    artifact_ref: str | None\n    cursor: str | None\n    item_count: int | None\n    truncated: bool\n    error_code: str | None\n    trust: str\n```\n`_preview_tool_data()` 只负责 UI/LLM preview，不再作为资源控制层。资源控制必须在 Broker/Connector 输出边界完成。\n\n### D. `_preview_tool_data` 的细节 bug\n字符截断后提示中的 total chars 使用了截断后的 `len(encoded)`，不是原始长度；并且切字符串会产生非完整 JSON。改为：先保存 `raw_len`，然后输出合法 JSON preview 对象，例如 `{preview: ..., meta:{truncated:true, raw_chars:...}}`。\n\n### E. Plan 必须成为执行约束\nL2/L3 的 plan 当前更接近 UI 说明。长期把 `current_step` 绑定 capability/precondition/postcondition；如果模型调用计划外工具，显式 `replan`，记录原因。\n\n### F. Tool lifecycle\n正确序列：`tool.requested` →（若需要）`approval.required` → `approval.resolved` → `tool.started` → `tool.completed|failed`。`tool.started` 只能在 connector 真正执行前发。\n\n### DoD\n- 单个 list/search 后，下一轮模型能看见结果。\n- 相同成功 signature 不会无理由执行 5 次。\n- 10MB structured data 不进入 Run.state。\n- approval 工具不存在假的 started。\n- bad JSON args 不执行 connector。\n
